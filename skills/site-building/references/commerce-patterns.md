# Принятые commerce-подходы

Применять к торговым сценариям, не к каждому сайту. Общее разделение слоёв —
[platforms.md](platforms.md). Исходники и лицензии зафиксированы в [реестре](../upstream.json).
Разбор сделан по конкретным файлам, не по обещаниям README; это не полный аудит
всего checkout пяти платформ. Следующие решения включены в основу сейчас.

## Каталог и варианты — Vercel Commerce + Medusa DTC

Стабильный option ID отделён от переведённой подписи. Выбранные значения доступны
через URL: refresh, ссылка и Back воспроизводят состояние. Изменение одного
значения сохраняет остальные параметры; фильтр/сортировка сбрасывает пагинацию
только соответствующего списка. Порядок и ключи не зависят от локализованного текста.

У товара различаются incomplete, invalid, missing combination, unavailable,
ambiguous и ready. Покупка возможна лишь при одном полностью определённом варианте;
сервер повторно проверяет его доступность. Нельзя угадывать товар при поддельном URL.
Для единственного варианта допустим предвыбор, если он однозначен. Смена варианта
согласованно меняет изображение, цену, остаток и ссылку, а не только подпись кнопки.
У нескольких групп опций проверить тупиковые сочетания и понятный сброс выбора.

Исполняемые извлечения: [variant-selection.mjs](../assets/commerce/variant-selection.mjs)
на основе Vercel и [option-filters.mjs](../assets/commerce/option-filters.mjs) на
основе Medusa. В них удалены зависимости Shopify/Medusa/Next/React, усилена
проверка значений и унифицированы повторяющиеся query-параметры. Это одна логика
для разных renderer, а не ещё одна независимая реализация внутри каждого блока.

Проверять: неизвестный ID; неполный выбор; отсутствующее сочетание; закончился
остаток после загрузки; несколько одинаковых сочетаний; длинные подписи;
сохранившиеся сортировка/кампания; Back; отсутствие результата и отказ провайдера.

## Цена и корзина — применяем принципы, не копируем чужую арифметику

Vercel показывает немедленный optimistic отклик, но его демонстрационный reducer
складывает `Number`-цены и заменяет tax/subtotal. В общей системе это не источник
денег. Medusa показывает цены из расчёта backend; её проверку через falsy нельзя
переносить: цена 0 не означает отсутствие цены.

Источник определяет currency, единицу суммы, точность, скидки, налог и доступность.
Адаптер нормализует их один раз; UI форматирует локаль через Intl и не делит
всегда на 100. Ноль, отсутствующее значение, неподдержанная валюта и ошибка —
разные состояния. «Цена от» не считается ценой выбранного варианта.

Для корзины: подтверждённый серверный snapshot + отдельное pending-намерение.
Optimistic отображение не подтверждает новый итог, налог, скидку или оплату.
Сериализовать конфликтующие записи на одну корзину или использовать серверные
ревизии; не принимать поздний ответ как более новый. Количество — конечное целое,
изменение по cart-line ID: одинаковый variant может иметь разные опции/подписки.
Локальный таймаут записи означает неизвестный результат, а не доказанный отказ;
перед повтором сверить backend. Не делать автоматический повтор неидемпотентного действия.

[mutation-lane.mjs](../assets/commerce/mutation-lane.mjs) — наш небольшой ресурс
для ограничения параллельных записей и обязательного снятия pending через finally.
Это не распределённая блокировка: другие вкладки и устройства требуют контракта
backend. Ошибка остаётся видимой; вернуть кнопку недостаточно без сообщения.
При необходимости параллельного редактирования вводить очередь намерений и тесты
ревизий вместо удаления защиты. Network read и commerce mutation имеют разные правила повтора.

Проверять: двойное нажатие; ошибка/таймаут; поздний ответ; 0; last-item removal;
скидка на всю корзину; разные валюты/регионы; устаревший остаток; восстановление
после refresh. Не объявлять заказ оплаченным по redirect/query-параметру.

## Пагинация и кэш — Hydrogen + Paper

[pagination.mjs](../assets/commerce/pagination.mjs) извлечён из Hydrogen:
cursor+direction и namespace для нескольких списков. Добавлены проверки размера,
разделение reset и сохранение фильтров. Provider переводит first/last/cursor в
аргументы своей платформы; UI сохраняет семантические ссылки и работает без
бесконечного скролла. При смене набора данных старый cursor не переиспользуется.

[cache-policy.mjs](../assets/commerce/cache-policy.mjs) использует подход Hydrogen
к явным HTTP-директивам. Personal/unknown/session unavailable и все mutation —
no-store; public только явно. Политика TTL относится к данным, не ко всему сайту.
Не кэшировать персональные HTML/цену по публичному ключу. Проверять Vary/CDN/cookies
и реальную стратегию framework: один заголовок не исправляет другой уровень кэша.

Из Paper принят единый реестр: ресурс → cache key scope → теги → TTL → события
инвалидации → затронутые страницы. Для ключа учитывать locale/channel/currency
и применимые фильтры. CMS изменение обновляет страницу и её списки; смена slug —
старый и новый URL. При неполном webhook payload использовать ограниченный
fallback в том же канале, а не бесконтрольный global purge. Подпись webhook,
защита replay и минимальные права обязательны для конкретного adapter.
Метаданные реестра могут обслуживать диагностику без секретов и клиентов.

Проверять изменение навигации/футера, редактирование товара, прежний URL, два
канала, две локали, ошибку сессии и webhook без части контекста. Default guest
нельзя подставлять при недоступной авторизации.

## Checkout и расширения — Paper

Принят подход явного registry доступных способов оплаты и отдельного контракта
их UI/server действий: capabilities, feature flags, submit mode, pending/error,
подтверждение статуса. Не смешивать разрешённый, недоступный, неизвестный и тестовый
gateway; dummy не включать в production. Возможности для UI подтверждает сервер,
публичный feature flag не является авторизацией. SDK и ключи остаются в своих слоях.

Шаги checkout имеют адресуемое состояние и Back; переход не стирает уже введённое.
Сервер проверяет предшествующие условия независимо от URL шага. Guest order URL
не раскрывает данные по угадываемому ID; доступ к заказу проверяется отдельно.
Транспортная ошибка сессии отличается от гостя. Платёжные секреты и сырые токены
backend не отправляются в browser storage, логи и документ передачи.

Это принятые архитектурные требования. FSL-код Saleor не скопирован и не
переведён в другую лицензию; реализация для Vendure/WooCommerce использует API
их версии. Не обещать отсутствие будущих изменений: провайдеры и контракты меняются.
Скилл должен заранее задать проверки этих границ, а не скрыть их за готовым UI.
