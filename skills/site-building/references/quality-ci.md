# Проверки качества — действующая основа Lighthouse CI

Применять к настоящим страницам и production build, не к отсутствующей витрине.
Документация: [Lighthouse CI configuration](https://googlechrome.github.io/lighthouse-ci/docs/configuration.html).
В скилле есть [рабочий конфиг](../assets/quality/lighthouserc.cjs), проверяемый
на изолированном компонентном стенде. Это наш конфиг по публичному API LHCI,
не копия его repository config: тот отключает ряд проверок для своих задач.

## Включение

1. Определить репрезентативные URL: главная, список, детальная страница, основной
   пользовательский сценарий. Для checkout использовать тестовые данные, не
   реальные платежи. Не тестировать персональные страницы публичным сервисом.
2. Добавить проверенную точную версию `@lhci/cli` в devDependencies и lockfile
   целевого проекта; в стенде набора проверяется 0.15.1. Не переносить его старые
   транзитивные зависимости в browser bundle. Проверять advisories и обновления.
3. Для static build указать SITE_AUDIT_DIST и SITE_AUDIT_URLS (localhost URL через
   запятую) и запустить `lhci autorun --config=путь/lighthouserc.cjs`.
   Для SSR заменить collect.staticDistDir на production startServerCommand,
   readiness pattern и URLs. Не запускать static-server поверх SSR output.
4. Проверки должны возвращать ненулевой exit code при нарушении бюджета. HTML/JSON
   сохранять локально или CI artifact; публикация отчёта с данными требует решения.

Конфиг запускает три измерения. LCP/TBT — median, CLS/размеры/доступность —
pessimistic: удачный одиночный прогон не маскирует дефект. Стартовые бюджеты
профиля: LCP 2500 ms, CLS 0.1, TBT 200 ms, script transfer 200000 bytes, total
transfer 1000000 bytes. Это выбранный проверяемый профиль, не обещание для любого
устройства и не всеобщее требование к весу сайта. До измерения целевого сайта
обосновать бюджет его сценариями; после нарушения исправить причину, не ослаблять
порог ради зелёного отчёта. Изменение согласованного бюджета документировать.

## Что не подменяется Lighthouse

100 accessibility не означает полное соответствие WCAG. Проверять клавиатуру,
фокус после переходов, assistive technology, 200% zoom, длинные подписи,
reduced-motion, touch и промежуточные ширины отдельно. TBT лабораторный proxy,
не измеренный полевой INP. Оценки dev machine не являются опытом посетителей:
после запуска нужен мониторинг реальных метрик в рамках разрешённой аналитики.

CI набора проверяет выбранные компоненты, не весь будущий магазин. Полный
сценарный набор включает ошибки провайдера, авторизацию, изменение данных,
миграции presets и чистую экспортированную копию. Проверки дизайна не заменяют
тесты commerce backend и не дают разрешения публиковать сайт.
