# Общая система и адаптеры платформ

## Порядок выбора

1. Зафиксировать реальный стек и версии. Для новых проектов основной профиль
   владельца — Payload для контента и Vendure для торговли. Существующий движок
   сохранять, если смена не входит в задачу. Сайту услуг Vendure может не требоваться.
2. Описать нейтральные данные и действия нужных сценариев, затем адаптер платформы.
3. Подключить компоненты к общему контракту, проверить отказ и реальные данные.
4. В передаче назвать точный режим интеграции и что действительно запускалось.

## Границы слоёв

| Слой | Содержит | Не содержит |
| --- | --- | --- |
| Дизайн | Семантические токены, типографику, CSS, SVG, структуру компонентов | Клиенты CMS, GraphQL-запросы, PHP-сессии |
| Представление | Компоненты/шаблоны, принимающие данные и действия | Собственное вычисление цены, контакты-дубли, секреты |
| Адаптер | Преобразование данных, ссылки, действия и ошибки платформы | Новую систему цвета/отступов |
| Сервер/источник | Доступ, CMS, каталог, остатки, налоги, корзину и оплату | Неподтверждённые бизнес-факты |

Цена передаётся с валютой и точностью источника; не предполагать две дробные
цифры для всех валют. Итог, доступность варианта и скидку подтверждает commerce
backend. Форматирование локали — одна функция. Недоступный источник отличается
от пустого каталога. Компоненту не передаются необработанные SDK-объекты.

## Payload + Vendure

Основной профиль: витрина — Next.js (App Router), за ней Vendure (торговля) и
Payload (контент). Конкретный порядок, запросы, ошибки и проверка готовой
витрины — [vendure.md](vendure.md) и [payload.md](payload.md); готовый код
серверного слоя — [assets/vendure](../assets/vendure/INTEGRATION.md). Ниже —
границы, общие для любого распределения данных.

Payload владеет страницами, навигацией, редакционными блоками, медиа и SEO.
Vendure владеет товарами/вариантами, ценами, остатками, каналами и заказами.
Товар в CMS ссылается на устойчивый идентификатор, не дублирует изменяемую цену.
Если данные распределены иначе в действующем проекте, документировать его контракт.

Схема CMS-блока содержит `type`, устойчивый `id`, версию и параметры. Один реестр
связывает схему, renderer и разрешённые варианты. Неизвестный блок обрабатывается
предсказуемо; миграция проверяется на сохранённых документах. В preview проверять
доступ к черновикам, источник сообщений и окружение; не открывать draft публично.

Кэшировать публичный каталог согласно версии фреймворка; не смешивать сессии
покупателей. Изменения через CMS/webhook обновляют соответствующие данные.
При смене опубликованного slug инвалидировать прежний и новый URL; проверять
сценарий отдельно от снятия с публикации. Не копировать webhook-пример без
проверки этой границы и затронутых страниц списка.
Повторять автоматически только операции, для которых повтор безопасен; платёж
и создание заказа требуют подтверждённой идемпотентности. Optimistic UI не
превращает клиент в источник истины об оплате/наличии.

Исходники для сверки: [Payload website template](https://github.com/payloadcms/payload/tree/main/templates/website),
[Vendure](https://github.com/vendure-ecommerce/vendure). Перед внедрением читать
конкретную версию и модуль. Лицензия backend не распространяется автоматически
на все примеры, изображения и сторонние расширения.

## WordPress / WooCommerce

Выбрать один маршрут: native block theme (`theme.json`, templates, patterns),
классическая/дочерняя тема (PHP/hooks) или headless со своим контрактом API.
Не добавлять React/Next только для применения скилла. В block theme связывать
семантические роли с `theme.json`; сохранить редакторскую управляемость и не
создать независимые значения в CSS и редакторе. В существующей теме учитывать
иерархию шаблонов и переопределения плагинов.

WooCommerce определяет commerce-действия, налоги, доставку и session. Проверять
совместимость выбранных Cart/Checkout Blocks либо традиционного checkout с
установленными расширениями. Тестировать в staging, не переписывать ядро.
Основания: [WordPress theme.json](https://developer.wordpress.org/themes/global-settings-and-styles/),
[WooCommerce Store API](https://developer.woocommerce.com/docs/apis/store-api/).

## OpenCart

Уточнить поколение OpenCart и тему: путь расширений и контракты отличаются.
Адаптировать Twig/контроллеры и данные через возможности выбранной версии,
сохраняя один CSS-контракт. Не править ядро ради оформления. Проверить язык,
валюту, варианты товара, корзину, сообщения ошибок и очистку кэша темы.
Основание: [OpenCart source](https://github.com/opencart/opencart).

## Честная универсальность

Общие принципы, токены и ресурсы переносимы. React-компонент не становится
PHP/Twig-шаблоном автоматически. Архив исходников адаптера не является
установочной темой, пока он не установлен и не проверен на целевой версии.
Профили выше — рабочая инструкция интеграции, не заявление о существовании
проверенных production-адаптеров для всех платформ.
